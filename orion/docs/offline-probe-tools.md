# Offline E5/E6 preparation

`opd_pilot.update_probe` has only freeze-batch, freeze-score, align, plan and compare
operations (`--spec FILE`). There is no train/execute mode or Slurm submission stage.
All JSON artifacts are new directories; filenames are readable. SHA256 digests live
only in metadata. Source checkpoints must be stopped before inspection/hash reading;
large checkpoint audits belong on compute nodes, not the login node.

Batch payload: purpose=e5_fresh_student_train, official_split=train, student_revision,
checkpoint_revision (must match), sampling, and ordered rows. Each row contains
sample_id, full tokens, prompt_length, response_mask (response-width), native_fields.
Native fields preserve the supplied JSON mapping including dtype/shape metadata
where applicable; this is an offline envelope, NOT a validated Experience serializer.
Do not omit native fields or use compact diagnostic records as a substitute for a
complete native training batch. Native capture/reconstruction awaits approved replay.

Score payload: batch_digest, teacher_revision, tokenizer_revision, backend,
temperature (explicit semantics should be recorded alongside it), rows. Each row
repeats sample_id/tokens/prompt_length/response_mask and adds teacher_log_probs and
valid_mask. Length, order, boundary, mask or finite-score failures block freezing.
No exclusions, retokenization or score normalization is performed. Model/tokenizer
metadata is preserved; numeric identity across tokenizers/backends still needs real
validation. align prints locations of differences.

Freeze specs contain input (JSON payload path), output (new bundle directory), and
for scores batch (frozen batch directory). load_bundle verifies envelope integrity.
Plan spec contains checkpoint, world_size, batch, scores={A: directory, B: directory},
branches_root. It audits archive structure/digests and alignment, proposes separate
A/B/AA-repeat paths without creating them, and references the unchanged checkpoint
for C. Structurally eligible never means restore validated or execution authorized.
Model revision claims in payloads require provenance review; hashes do not establish
that a batch was actually generated by a particular checkpoint.

Compare spec: results={C: path or null, A: path or null, B: path or null},
protocol_digest, metrics=[explicit scalar names]. Input summaries contain
protocol_digest, metrics and optional update_evidence (counts, LR, grad/clip/delta,
sample IDs). Report preserves missing metrics/results as null and produces A-C,
B-C, B-A. Reuse selection_analysis/branch_analysis/paired_stats for scientific
aggregation; this comparator is descriptive and does not invent uncertainty.

`opd_pilot.confirmation freeze --spec FILE` takes protocol and output. Required
protocol fields are listed in confirmation.FIELDS; template is in
orion/templates/confirmation-protocol.json. All scientific choices remain null until
selected. It checks exact task counts, disjoint task IDs, budgets/seeds and an explicit
results-not-seen declaration, stores task content digests, and publishes a new lock.
`verify --spec FILE` takes directory and verifies protocol and task-file integrity.
This cannot prove someone never viewed results, enforce a submitted job's budget or
authorize execution. Existing evaluators/jobs must use the frozen protocol when later
approved. E6 may confirm E2–E4 directly; E5 completion is not a prerequisite.

Do not use confirm_holdout to generate update batches. Formal A/B and confirmation
jobs remain unsubmitted. See native_update_path.md for the specific pending patch.
